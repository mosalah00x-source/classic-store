# Classic Store — قاعدة البيانات النهائية (الإصدار الأول)

**التقنيات:** PostgreSQL 16+، Spring Boot / Java 21، Flyway. **نطاق التشغيل:** مصر (EG)، الجنيه المصري (EGP)، عدة مخازن داخل مصر، منتجات مادية فقط، شراء بحساب أو كزائر.

## التشغيل

أنشئ قاعدة بيانات فارغة مع مستخدم يمتلك صلاحية إنشاء الإضافات (`pgcrypto`, `citext`, `btree_gist`) والمخططات، ثم شغّل Flyway على مجلد migrations:

```bash
flyway -url=jdbc:postgresql://localhost:5432/classic_store -user=classic -password=CHANGE_ME -locations=filesystem:./migrations migrate
```

أو شغّل الملف المجمّع `classic_store_all.sql` عبر `psql -v ON_ERROR_STOP=1 -d classic_store -f classic_store_all.sql` على قاعدة فارغة فقط. لا تشغّل الملف المجمّع بجانب Flyway على القاعدة نفسها.

## الجداول حسب المجال

| المجال | الجداول | الغرض |
|---|---|---|
| الهوية والعناوين | `users`, `addresses`, `countries`, `governorates`, `cities` | الحسابات وعناوين العملاء والتقسيم الجغرافي |
| الكتالوج | `brands`, `categories`, `products`, `product_categories`, `product_variants`, `product_images` | المنتجات المادية والمتغيرات والأسعار والصور |
| المخزون | `warehouses`, `inventory`, `inventory_movements` | الرصيد الفعلي والمحجوز وسجل الحركات |
| التسوق | `carts`, `cart_items`, `coupons` | السلة والخصومات |
| الطلبات | `orders`, `order_items`, `order_status_history` | الطلبات مع snapshots للأسعار والعناوين |
| التنفيذ | `fulfillments`, `fulfillment_items`, `inventory_reservations` | التخصيص والحجز والشحن |
| الدفع | `payments`, `payment_events`, `refunds` | محاولات الدفع والأحداث والاسترداد |
| الشحن والمرتجعات | `shipping_zones`, `shipping_rates`, `returns`, `return_items` | التسعير والمرتجعات |
| التكامل | `outbox_events`, `settings` | أحداث التكامل والإعدادات |

## سياسة أقرب مخزن (nearest)

1. خزّن إحداثيات عنوان الشحن في `orders.shipping_latitude` و`shipping_longitude`، بعد التحقق منها؛ لا يكفي اسم المحافظة لتحديد الأقرب.
2. `store.rank_warehouses(order_id)` تعرض المخازن النشطة في بلد الطلب التي **تغطي جميع بنود الطلب**، مرتبة حسب مسافة Haversine بالكيلومترات ثم `priority`.
3. `store.reserve_order_at_nearest_warehouse(order_id, 15)` تختار أول مخزن متاح، وتقفل صفوف المخزون وتعيد التحقق قبل زيادة `reserved`. تُعيد `NULL` إن تعذر تخصيص الطلب في مخزن واحد.
4. عند الإلغاء: `store.release_order_reservations(order_id)`؛ عند تأكيد خصم البضاعة فعليًا: `store.consume_order_reservations(order_id)`.
5. المسافة هنا **خط مستقيم على سطح الأرض**، وليست زمن قيادة. إذا كانت الأولوية للأقرب على الطرق فعليًا، احسب زمن الرحلة بخدمة خرائط في التطبيق مع الإبقاء على فحص المخزون وقفل الصفوف في قاعدة البيانات.

**مهم:** جميع عمليات تعديل المخزون يجب أن تمر عبر خدمات موحدة/معاملات SQL؛ لا تسمح بتعديل `on_hand` و`reserved` عشوائيًا. يوصى بتنفيذ حجز المخزون داخل معاملة قصيرة ثم تأكيد الدفع بمعاملة أخرى. وظيفة انتهاء الحجز المجدولة يجب أن تقفل الطلب أولًا ثم تفك الحجز؛ لا تعتمد على مرور الوقت وحده لتغيير الحالة. لزيادة موثوقية عمليات الدفع، استخدم idempotency keys وأحداث webhook موثّقة.

## Guest Checkout

`orders.user_id` قابل لأن يكون `NULL`، بينما بيانات العميل والعنوان محفوظة في الطلب. يُحفظ البريد/الهاتف للزائر في `guest_email` / `guest_phone`؛ و`customer_name`, `customer_phone` إلزاميان. لا تُنشئ حسابًا ضمنيًا للزائر. ينبغي حماية واجهة تتبع الطلب برمز وصول عشوائي محفوظ بصورة hash في طبقة التطبيق أو جدول منفصل، وعدم كشف الطلب اعتمادًا على رقم الطلب فقط.

## ثبات البيانات التاريخية

`order_items` تحفظ SKU واسم المنتج وسعر الوحدة والخصم وقت الشراء، و`orders.shipping_address` تحفظ JSON لعنوان الشحن كما كان وقت الطلب. لا تُعد حسابات الطلبات القديمة بالاعتماد على أسعار الكتالوج الحالية. يجب أن يتحقق التطبيق من تطابق `orders.subtotal` مع مجموع `order_items.line_total`، ومن صحة الضريبة والشحن والخصم قبل تأكيد الطلب.

## متطلبات تطبيقية قبل الإنتاج

- صلاحيات قاعدة بيانات منفصلة: مستخدم migrations له DDL، ومستخدم التطبيق DML محدود.
- التحقق من webhook signatures وعدم تسجيل بيانات بطاقات حساسة؛ حفظ مراجع مزود الدفع فقط.
- فهارس إضافية بعد تحليل `EXPLAIN ANALYZE`، ونسخ احتياطية مع اختبار الاسترجاع، ومراقبة المعاملات والتنافس.
- فرض انتقالات الحالات الصحيحة في خدمات Spring Boot مع اختبارات تكامل PostgreSQL (وليس H2).
- التحقق من اتساق `fulfillment_items` مع الطلب الأصلي، ومن سقف الكميات المرتجعة/المستردة عبر الخدمات أو triggers قبل الإنتاج.
- التحقق من أن `governorate_id` و`city_id` يتبعان بلد وعنوان المخزن أو العميل، وتحديد سياسات الخصوصية والاحتفاظ بالبيانات.
- إضافة سياسة صريحة عند غياب الإحداثيات: طلب عنوان أدق أو استخدام توزيع إداري بديل؛ الدالة الحالية ترفض التخصيص دون إحداثيات.
